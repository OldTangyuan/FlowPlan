## 1. 架构总览：Feature-First 分层架构

### 1.1 一张图看懂

```
┌─────────────────────────────────────────────────────────┐
│                    presentation（表现层）                  │
│   UI 页面（列表页/编辑页）+ Riverpod 状态管理（Controller）   │
├─────────────────────────────────────────────────────────┤
│                    application（应用层）                   │
│   业务逻辑：TodoController / AIService（未来）              │
│   —— 调用 domain 接口，不关心数据存哪、UI 长啥样             │
├─────────────────────────────────────────────────────────┤
│                       domain（领域层）                     │
│   Todo 模型 + TodoRepository 抽象接口                      │
│   —— 整个架构的"宪法"，最稳定，不依赖任何第三方库              │
├─────────────────────────────────────────────────────────┤
│                        data（数据层）                      │
│   SqliteTodoRepository：用 SQLite 实现 TodoRepository      │
│   —— 唯一知道"数据存在数据库里"的地方                       │
└─────────────────────────────────────────────────────────┘
```

### 1.2 依赖规则（架构的"法律"）

真实项目架构最重要的一条规则，叫**依赖方向**：

```
presentation → application → domain ← data
```

翻译成人话：
- **上层可以调用下层，下层绝不知道上层的存在**。
- `domain` 在最中心，谁都不依赖，谁都得遵守它的接口。
- `data` 实现 `domain` 定义的接口，但 `domain` 不知道自己被谁实现。

> 💡 **和 Python 的类比**：这就是"面向接口编程"。像这样：
> ```python
> # domain 层定义"接口"（抽象基类）
> class TodoRepository(ABC):
>     @abstractmethod
>     def get_all(self) -> list[Todo]: ...
>
> # data 层实现它（SQLite 版）
> class SqliteTodoRepository(TodoRepository):
>     def get_all(self) -> list[Todo]:
>         # 真的去查数据库
>         ...
>
> # presentation 层只管用接口，不在乎实现
> repo: TodoRepository = SqliteTodoRepository()
> ```
> 将来换成云端存储，只要写一个 `CloudTodoRepository`，**UI 一行都不用改**。

### 1.3 为什么这样分（对初学者最重要的解释）

初学者最常见的错误：所有代码堆在页面里（"面条代码"）。
- 页面里直接写 SQL → 换数据库要改页面。
- 页面里直接调 AI → AI 换供应商要改页面。

分层之后：
| 变化 | 只动哪一层 |
|------|-----------|
| 数据库从 SQLite 换云端 | data |
| 加日历视图 / 改 UI 样式 | presentation |
| 加 AI 自动排序功能 | application（新增服务） |
| 任务模型加字段（如"标签"） | domain + 连带 data |

**每一层只做自己该做的事，这就是真实项目能长期维护的核心秘密。**

        ├── data/
        │   ├── datasources/
        │   │   └── todo_database.dart    # SQLite 建表 + 增删改查 SQL
        │   └── repositories/
        │       └── todo_repository_impl.dart  # 接口的 SQLite 实现
        ├── application/
        │   └── todo_controller.dart # 业务逻辑（Riverpod 状态管理）
        └── presentation/
            ├── pages/

            │   └── todo_edit_page.dart    # 新增/编辑页（共用）
            └── widgets/

                └── todo_filter_bar.dart   # 筛选栏（全部/未完成/已完成）

### 2.1 每个目录的职责（一句话版）

| 路径 | 职责 | 类比 Python |
|------|------|-------------|
| `main.dart` | 启动 App | `if __name__ == "__main__":` |
| `app.dart` | 全局配置（主题/路由） | Django 的 settings.py |
| `core/` | 全局共享的东西 | 项目根目录的 utils/ |
| `domain/models/todo.dart` | 任务的"定义" | `@dataclass class Todo` |
| `domain/repositories/` | 定义"存取任务"的接口 | 抽象基类 ABC |
| `data/datasources/` | 具体存哪（SQLite） | `sqlite3.connect(db)` |
| `data/repositories/` | 接口的 SQLite 实现 | ABC 的实现类 |
| `application/` | 页面和数据的桥梁 | ViewModel / 业务逻辑层 |
| `presentation/` | 用户看到的一切 | 前端模板 |

## 3. 核心设计决策详解

### 3.1 决策一：Todo 模型用不可变类（immutable）

Dart 的惯例：数据模型用 `final` 字段（不可变）＋ `copyWith()` 方法。

```dart
class Todo {
  final String id;
  final String title;
  // ...
}
```

> 💡 **为什么？** 防止"数据被偷偷改了还不知道"。Python 里如果你写 `todo.title = "x"` 没人拦你；Dart 里字段是 `final`，编译期就报错。修改用 `copyWith` 产生**新对象**，更安全、更利于 UI 刷新检测。

### 3.2 决策二：接口用 `abstract class` + `sealed` 风格

```dart
abstract interface class TodoRepository {
  Future<List<Todo>> getTodos();
  Future<void> addTodo(Todo todo);
  // ...
}
```

Dart 3 的 `abstract interface class`：接口只能被实现，不能被继承（比 Python 的 ABC 更严格）。

### 3.3 决策三：异步用 `Future` / `async` / `await`

数据库读写、AI 调用都是**耗时操作**，绝不能阻塞 UI。

> 💡 **和 Python 的类比**：Dart 的 `Future<T>` ≈ Python 的 `asyncio.Task` / `await`。
> ```python
> # Python
> async def get_todos():
>     return await db.query("SELECT ...")
> ```
> ```dart
> // Dart
> Future<List<Todo>> getTodos() async {
>   return await _db.query('SELECT ...');
> }
> ```
> 语法几乎一样！你在 Python 学的 async/await 知识**直接迁移**。

### 3.4 决策四：Riverpod 管理状态

TODO App 的核心状态：**当前任务列表** + **当前筛选条件**。

```
Provider（任务仓库） → Controller（业务逻辑） → UI 自动刷新
```

- `todoRepositoryProvider`：全局唯一的数据仓库实例（依赖注入）。
- `todoControllerProvider`：持有任务列表、筛选条件，暴露 `add/update/delete/toggle` 方法。
- UI 通过 `ref.watch(...)` 监听，数据一变页面自动重绘。

> 💡 这相当于 Python 里的**全局单例 + 观察者**，但 Riverpod 把它做成了类型安全、可测试的完整方案。

### 3.5 决策五：SQLite 版本管理（为未来升级预留）

数据库建表时带 `version`，sqflite 支持 `onCreate`（首次建表）和 `onUpgrade`（版本升级迁移）。

```dart
final _db = await openDatabase(
  path,
  version: 1,                // 当前版本
  onCreate: (db, v) => db.execute('CREATE TABLE ...'),
  onUpgrade: (db, oldV, newV) { /* 未来加字段时在这里 ALTER TABLE */ },
);
```

> 💡 这就是"面向未来"的体现：**现在不做迁移逻辑，但把迁移的钩子留好**。v0.2 加字段时，把 version 改成 2，在 onUpgrade 里写迁移 SQL，用户数据不丢失。

## 4. 未来 AI 接入的技术路线（本版预留了什么）

这是你最关心的部分——**AI 怎么接进来**。本版已经把地基打好：

### 4.1 预留点 1：`TodoRepository` 抽象接口

AI 管理任务 = AI 调用 `addTodo / updateTodo / deleteTodo / getTodos`。
本版已经定义好这些接口，未来 AI 服务只需：

```dart
// 未来：application/services/ai_service.dart（v0.2）
class AIService {
  final TodoRepository _repo;  // 注入接口
  Future<void> parseAndAddTodo(String userMessage) async {
    // 1. 调大模型 API，把自然语言解析成结构化任务
    // 2. 用 _repo.addTodo(...) 添加
  }
}
```

### 4.2 预留点 2：`dueDate` 字段

AI 排期的前提是任务有截止日期。本版 Todo 模型已含 `dueDate`（可为空），UI 暂不展示，未来直接可用。

### 4.3 预留点 3：`application` 层空位

AI 服务属于 `application` 层（业务逻辑），本版已经为它留好位置，到时候新建一个 `ai/` 功能目录即可，不侵入现有代码。

### 4.4 预留点 4：Riverpod 依赖注入

AI 服务创建时需要 API Key、HTTP Client 等配置，Riverpod 的 Provider 体系天然支持——在 `main.dart` 里注册，全局可用。

## 5. 数据流（一次"新增任务"的完整旅程）

以"用户点保存新增任务"为例，看数据怎么流动：

```
1. UI（编辑页）用户填好标题，点"保存"
        │
        ▼
2. TodoEditPage 调用 controller.addTodo(title, priority)
        │
        ▼
3. TodoController（application）创建 Todo 对象
        │
        ▼
4. TodoController 调用 repo.addTodo(todo)   ← 用的是 domain 接口
        │
        ▼
5. SqliteTodoRepositoryImpl（data）执行 INSERT SQL
        │
        ▼
6. 数据库写入成功
        │
        ▼
7. TodoController 重新加载列表，状态更新
        │
        ▼
8. Riverpod 通知所有监听的页面 → 列表页自动刷新
```

**关键点**：UI 只认识 `TodoController`，`TodoController` 只认识接口 `TodoRepository`，接口背后是 SQLite。每一环都解耦，每一环都可替换。

## 6. 错误处理策略

| 场景 | 处理方式 |
|------|----------|
| 数据库打不开 | 启动时 try-catch，显示错误提示 |
| 标题为空 | UI 层校验，禁止保存 |
| 写入失败 | Controller 捕获异常，SnackBar 提示用户 |
| 未来的 AI 调用失败 | application 层捕获，降级为"手动添加"提示 |

> 💡 Dart 的异常体系和 Python 几乎一样：`try { } on Exception catch (e) { }` ≈ Python 的 `try/except`。
